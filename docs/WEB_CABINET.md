# Веб-кабинет партнёра: Telegram Login

Адрес: https://api.нейроныч.online/cabinet (в production HTTP доступ не используется).

## Авторизация

Используется официальный Telegram Login Widget (callback), привязанный к существующему
Telegram-боту Нейроныча. Widget передаёт JSON в POST /cabinet/telegram без
Telegram auth-параметров в URL. Сервер проверяет HMAC-SHA256 по SHA256 токена
бота, auth_date (максимум 5 минут), браузерный CSRF
challenge с TTL 5 минут и точный Origin публичного API.

Затем по доверенному Telegram ID выбирается только действующий аккаунт
партнёра. Неизвестному или заблокированному Telegram ID новый аккаунт не
создаётся. В Redis на 12 часов сохраняется только отображение хеша случайного
session token на partner_id. Браузер получает Secure, HttpOnly, SameSite=Strict,
__Host- cookie. Logout инвалидирует сессию в Redis.

Данные страницы получают partner_id исключительно из серверной сессии:
чужой partner_id нельзя передать в query или body. История показывается
ограниченными (last N) наборами без SQL-доступа к чужим тенантам.
API-ключи отображаются только с префиксом, никогда в полном виде.

На первом этапе веб-кабинет показывает профиль, баланс, ключи, генерации,
ledger и счета. Создание ключей, пополнение и поддержку пользователь выполняет
через существующего Telegram-бота. Это не расширяет полномочия клиентского API.

## Требуемая конфигурация

Используются существующие настройки: TELEGRAM_BOT_TOKEN, TELEGRAM_BOT_USERNAME,
PUBLIC_API_BASE_URL и REDIS_URL. Новые секреты, миграции и настройки тарифов
не требуются.

**Обязательная операция владельца бота в BotFather:** привязать домен
api.нейроныч.online (ASCII/punycode: api.xn--e1aikcel5c5a.online)
к @apineurobrobot с помощью /setdomain или панели Web Login/Allowed URLs.
Без разрешённого домена Telegram может не отобразить окно входа; сайт и API
при этом могут отвечать 200/ready. Перепроверять привязку после изменения домена.

## Acceptance / smoke

1. GET /cabinet без сессии = 200, Telegram widget и Link в навигации.
2. Подлинный интерактивный вход под действующим Telegram ID = кабинет этого
   партнёра. Убедиться, что баланс совпадает с PostgreSQL.
3. Вход неизвестного/приостановленного пользователя = 403; нет нового партнёра.
4. Поддельный HMAC, старый auth_date, неверный CSRF и Origin = отказ.
5. GET /cabinet при валидной сессии не показывает данные другого партнёра.
6. POST /cabinet/logout очищает cookie и запись Redis.
7. На рабочем production сравнить /api/v1/readiness.revision с SHA релиза и
   проверить журнал app/nginx на ошибки после выкладки.

Без реального входа через Telegram с человеческого браузера нельзя отмечать
полный E2E Login PASS: CI проверяет подписи и маршруты на синтетических данных.


## Полноценный партнёрский портал (релиз OpenRouter-style)

Новый интерфейс поверх прежнего проверенного Telegram Login Widget. Структура
вдохновлена паттернами панелей API-провайдеров, но UI полностью фирменный.
Адрес остался прежним: /cabinet. Доступ — только через действующего партнёра.

| Раздел | Рабочие возможности |
| --- | --- |
| Обзор | баланс и кредитный лимит; расходы, запросы и последние операции |
| Аналитика | периоды 7/30/90 дней, тренды запросов и расходов, разбивка по моделям |
| Журнал запросов | статус, модель, стоимость, дата, фильтры, пагинация, детали и экспорт CSV |
| Модели | только опубликованные или персонально разрешённые, розничный тариф партнёра |
| API-ключи | создание, одноразовый показ секрета, отзыв, настройка webhook и подписи |
| Баланс | текущий баланс, кредитный лимит, оплачиваемые счета, создание нового счёта |
| Счета | провайдер, сумма, статус, ссылка на оплату, отмена допустимых счетов и CSV |
| Ledger | список рублёвых операций, фильтрация и экспорт без секретов |
| Настройки | организация, Telegram ID, email для чеков, выход из Redis-сессии |

### Авторизация и безопасность

- Браузер не хранит партнёрские API-ключи. Используется __Host-
  HttpOnly/Secure/SameSite=Strict cookie с Redis-сессией.
- Любой запрос и любое изменение жёстко привязаны к partner_id из сессии,
  а не из URL, формы или JS.
- Все POST требуют CSRF HMAC по cookie-сессии и точного Origin, сверяемого
  с PUBLIC_API_BASE_URL.
- API-ключ показывается целиком лишь в ответе на создание; чтение ключей
  выдаёт префиксы. HTML/CSV — Cache-Control: no-store.
- Отзыв ключа использует проверенную бизнес-логику Dashboard API;
  обновление webhook проходит существующий HTTPS/SSRF validator.
- Создание платежа идёт исключительно через существующий create_invoice
  (idempotency_key + проверенные ограничения на сумму и email). Никаких
  прямых начислений на баланс веб-портал не делает.
- CSV-экспорт ограничен 1000 строками и нейтрализует формулы для spreadsheet
  импорта; prompts и ключи в экспорт не попадают.
- Страница не показывает draft-модели и внутреннюю закупочную стоимость.

### Что не реализовано как возможности OpenRouter

Сервис по продуктовой спецификации — B2B с одним Telegram-идентификатором
на партнёра, без multi-seat workspaces. Поэтому здесь нет копируемых
OpenRouter-опций, для которых отсутствует бэкенд: BYOK provider routing,
org members / RBAC, per-key spending guardrails, автоматического списания с
карты без активного провайдера, конструкторов пресетов и автоматических
провайдерских fallback controls. Такие функции нельзя подменять
неработающими переключателями: нужны отдельные схемы БД, enforcement
в inference, финансовые тесты и UI.

### Release verification

- GET /cabinet без сессии: Telegram login.
- GET /cabinet с тестовым партнёром: реальные разделы и tenant isolation.
- POST /cabinet/action: неподписанный и чужой Origin отклоняются.
- New key: секрет показывается один раз, после отзыва API key не активен.
- Payments: повтор по idempotency_key обрабатывает existing payment service,
  списаний и прямых начислений через веб нет.
- CSV и Logs не раскрывают данные другого партнёра.
- На production /api/v1/readiness должен вернуть SHA целевого main, без
  ошибок на /cabinet и /ui/portal.css; для E2E Telegram нужен реальный
  интерактивный вход с привязанным через BotFather доменом.

## Документация и публичный каталог

- В боковом меню кабинета и в верхней панели есть ссылка «Документация»
  на /guide?lang=ru, рядом — «Каталог моделей» на /prices.
- /docs и /guide остаются двуязычным reference с рабочими примерами и добавляют
  быстрые переходы, поиск по оглавлению и копирование API base URL.
- /models, /price, /prices показывают один публичный каталог: Model ID, категорию,
  режим, разрешение, тариф в RUB, единицу тарификации, API endpoint и ссылку на справку.
- База каталога: только Model.status=production и актуальная PartnerPrice.
  Restricted, draft и закупочная стоимость не публикуются; персональные
  тарифы по-прежнему доступны только внутри кабинета.
- JS фильтры и сортировка — только улучшение: без JavaScript цены остаются
  в семантической HTML-таблице. Endpoint берётся из контракта моделей;
  версии CSS и JS повышены для корректного обновления кэша.
- Docs-домен по-прежнему изолирован от приватного кабинета.

Проверки: /docs?lang=ru, /docs?lang=en, /models, /price, /prices,
ссылка в авторизованном /cabinet, scope docs-хоста, /v1/models
и тесты регрессий. Изменений в биллинге и провайдерах нет.
